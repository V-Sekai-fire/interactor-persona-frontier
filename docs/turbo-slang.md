## Consequence for the design
A CPU kernel must not rely on buffer atomics. Write the fixpoint so each variable's bounds are written by one thread (a gather per
variable, or one pass per constraint class) or keep the CPU loop single-writer, and keep a separate atomic path for CUDA. This is a
risk to the plan's "one source for CPU and GPU": the claim holds only for the non-atomic subset.

## P2 copy of pir.hpp (2026-11-24): `slang/turbo/pir.slang`, `slang/turbo/probe.slang`
Copied: `ask`, `itv_div`, `num_fdiv/cdiv/tdiv/ediv`, `den_fdiv/cdiv/tdiv/ediv`, `mul_inv`, `deduce`, the battery `tdiv/fdiv/cdiv/ediv/emod`, `fjoin`, and an `Itv` with `meet`/`join`.
Compiles to `-target cpp` and `-target cuda` as a library; **does not compile with an entry point** (`probe.slang`) because of recursion:
- spirv and cuda: `error[E55201]: recursion not allowed` in `den_fdiv`, `den_cdiv` (they call themselves on split intervals).
- cpp: `error[E99997] ... unexpected: circularity during codegen`.
Recursion depth in the source is at most two levels (a split of `x`, then a split of `y`), so the next step is to unroll those calls into
fixed-depth copies, keeping each rule's text. That is the first departure from a literal copy and is forced by the compiler.
Departures so far: `deduce` writes into the three intervals with `meet` instead of calling `sub->embed` (the caller stores them); `ask` for
`MUL` spells `r2 == 0` as both bounds equal 0; values are `int`. Nothing here has been run, and none of it is tested against Turbo.

## P2 format and kernel (2026-11-24)
Format: store `lower[v]`, `upper[v]` (`int`), bytecodes `code[i] = (op, x, y, z)` meaning `x = y op z` with the operator codes of `turbo/Turbo/Pir.lean`, `control[0]` the bytecode count.
`turbo/Turbo/Fixpoint.lean` adds `embed`, `deduce_bytecode` (load three variables, `deduce`, embed the three results in order, as `PIR::deduce(bytecode)`) and the entry `fixpoint`:
Gauss-Seidel sweeps until one changes nothing or a variable is bot; it writes the rounds to `control[1]` and a bot flag to `control[2]`. One thread, no atomics, so it compiles for cpp.
Reference: `slang/turbo/oracle/dump.cpp` reads a FlatZinc file, ternarizes and interprets it into Turbo's `PIR` over a `VStore`, prints the store and the bytecodes, runs Turbo's `GaussSeidelIteration`, and prints the store again.
Steps for a level: `elixir tools/party_saga.exs dump TRACK G SEED OUT.dzn`; `minizinc -c --solver turbo.gpu.release --fzn L.fzn party-saga.mzn OUT.dzn` (Turbo's `msc` on `MZN_SOLVER_PATH`);
rewrite unit clauses `bool_clause([x],[])` to `bool_eq(x,true)` and the `solve` line to `solve satisfy` (the lala ternarizer rejects a unary `∨`, and `PIR` cannot interpret the search annotation);
`dump L.fzn > L.dump`; `elixir tools/turbo_fixpoint.exs L.dump`.
Result (CPU, one thread, `g++ -O2`): the final store equals Turbo's on every variable for
scout (g=2, seed 1) 4,869 variables and 4,544 bytecodes, 9 rounds, 6 ms; party (g=4, seed 2) 40,559 and 39,810, 11 rounds, 36 ms; saga (g=6, seed 3) 306,406 and 304,170, 13 rounds, 230 ms.
Not done: Turbo's simplifier and `preprocess_tcn` (the dump takes the plain ternarized formula), search, the objective, the GPU path (Jacobi sweeps with atomics), `ask`/extraction.
## P3 search and branch and bound (2026-11-24)
`turbo/Turbo/Solve.lean` is `barebones_dive_and_solve.hpp` for one thread per block on the CPU target: `propagate` (fixpoint, then the `ask` scan for a solution), `split` with the five variable orders and four value orders,
decisions with ropes, backtracking from the root snapshot, objective tightening from `appx_best_bound`, and the dive over `2^power` subproblems. `tools/turbo_solve.exs` runs it on a dump of Turbo's own preprocessing
(`slang/turbo/oracle/cp_dump.cpp`: parse, ternarize, simplify, strategies, objective), with `--blocks`, `--power`, `--stop-nodes`.
Two guarded departures from the source, both only on a path where the source reads out of range: a failed `split` is read from its return value (the source checks `decisions[depth-1]`, which is the previous decision), and a satisfaction problem (no objective) stops at its first solution (the source's barebones mode is minimization only).

## Timeslicing through the planner (owner, 2026-11-24)
The game on this machine is real time and the host has 8 threads, so the solver may use the machine only in free time, one bounded step at a time, planned by the planner and able to restart (owner: "ipyhop is reentrant and can restart").
- The search is a state machine (`turbo/Turbo/Solve.lean`, `state[b][phase]`): `solve` runs until a node budget (`control[13]`) is used and returns after any whole iteration; the next call continues. All state is in buffers; the driver (`tools/turbo_solve.exs`) writes them to a checkpoint file after each slice. Slices of 37, 150 or 1000 nodes, each a fresh process, give the same node count, solutions, fails and objective as one run (scout: 629, 8, 307, 511).
- Domain `turbo_solve` (`entities/domains/turbo-solve.yamlld`, imported into SQLite like the others): action `wait-free(m)` (the host load is under the limit) and `solve-slice(m, l)` (the effect claims the level is done; the runtime reads the real status and plans again), methods `wait-free-host`, `solve-slice-of`, `solve-level` with a `finished` alternative. Problems `turbo_solve_party_busy | free | done` plan to wait then slice, slice, and nothing.
- `tools/turbo_player.exs LEVEL.cp` is the loop: observe (load average under `--max-load`, default 4; GPU under `--max-gpu` percent, default 30), put the observation in a fresh database as a problem, ask the planner, run the first step (the slice runs niced, one thread), repeat. Tested on scout: waits while the GPU is busy, 5 slices of 150 nodes gives the same result, stopping after 2 slices and starting again resumes at node 300.
## Guest ELF under libriscv, nodes and work stealing (2026-11-24)
- The solver is a riscv64 static guest ELF: the Slang `-target cpp` text of `solve` plus `guest/guest_main.cpp`, compiled with `clang++ --target=riscv64-unknown-linux-gnu -march=rv64gc` against `/mnt/fire/5-repository/riscv64-sysroot` (the flags of its `toolchain.cmake`). `guest/host/turbo_host.cpp` runs it with libriscv (CMake project `guest/host`, libriscv at `/mnt/fire/6-datasource/libriscv`, binary translation off) and loops `machine.resume(budget)`, so a step is an instruction budget, deterministic and able to stop anywhere (libriscv `Machine::resume`, `instruction_limit_reached`, `serialize_to`).
- A libriscv option is required: `MachineOptions::ignore_text_section = true` (`rvlinux -I`). By default libriscv bounds jumps by `.text`, and a static glibc keeps `.iplt` beside it, so the guest died with "Illegal opcode executed" on its first `memcpy`. The `lean-guest` recipe (`cmake/run_guest.cmake`) names the same fix.
- Scout under the guest equals native: 629 nodes, 307 fails, 8 solutions, objective 511, exhaustive; the host reports the improving bound while it runs.
- `turbo/Turbo/Solve.lean` has an external mode (`control[14]`): at each subproblem boundary the block waits in `phaseAwait`, and `control[15]` cancels the subproblem in hand. `tools/turbo_cluster.exs` is a coordinator and worker nodes over Erlang distribution (cookie, `--name`, so a worker can be on another machine; `epmd` under `~/.pixi/envs/elixir/lib/erlang/erts-*/bin`), with the messages in `service/turbo-cluster.asyncapi.yaml`.
- Each node says `cpu` or `gpu`; the coordinator measures nodes per second per node. Work stealing is the failure path used on purpose: an idle node takes a subproblem from a node at least 1.5 times slower that has held it for `--steal-after-ms`, by presuming that node dead for it; the first copy to finish wins and the other is cancelled. A node that really dies is requeued the same way; a node with nothing to do waits while any subproblem is in flight.
- Tested on loopback with separate OS processes, scout: 1 node 629 nodes; 3 nodes, 8 subproblems, objective 511; 4 nodes, 32 subproblems, 511; one node killed at its first assignment, the survivors finish all subproblems, 511. One fast `gpu` node and two throttled `cpu` nodes (`--slow-us`), 32 subproblems: 3.6 s with stealing (one steal, one copy cancelled), 30.6 s without, objective 511 both. The `gpu` kind is a label and a speed prior today; the node behind it is the same guest. A real GPU node needs a Slang GPU kernel (or Turbo's GPU solver given the subproblem protocol) behind the same frames.

## GPU: the cooperative kernel (2026-11-24)
- `turbo/Turbo/Coop.lean` is the search for a 256-thread workgroup per block, as Turbo's own kernel: all threads share a node's fixpoint sweep, the unentailed-propagator scan, the variable selection and the store copies; thread 0 runs the serial search logic; control is uniform and barriers separate every write from the reads that follow. The store is changed with `InterlockedMax` (lower) and `InterlockedMin` (upper), the meet. The shared best bound and next-subproblem counter use `InterlockedMin`, `InterlockedAdd`, `InterlockedMax`. Entailed propagators leave the sweep (a per-block active list, reset after every restore, compacted by warp).
- Build: `turbo_emit solve-coop` then `slangc -target cuda -entry solve`, then `nvcc -arch=sm_89 -cubin` (nvcc from Turbo's pixi environment). `guest/gpu/turbo_gpu.cpp` is the CUDA driver-API host: it loads the cubin, fills the global parameter block, and runs bounded launches (`SLICE_NODES` nodes per block per launch). `TURBO_PROGRESS`, `TURBO_MAX_LAUNCHES` and the best-bound log help watching a run.
- Equal to Turbo: scout, one block: 629 nodes, 307 fails, 8 solutions, objective 511, exhaustive. Party, 2,000 nodes: 995 fails, 3 solutions, 809. With one block and a split (`power` 3, 5, 8) the node counts equal Turbo's exactly: 640, 658, 700, so the dive, the skipping of failed subtrees and the subproblem order are the same. With many blocks the counts differ with timing, as Turbo's do (scout, 256 blocks, 8,192 subproblems: 13,345 nodes against Turbo's 10,868).
- Speed: party, one block, one node per launch: mean 1.97 ms, max 7.4 ms per launch, 2,000 nodes in 4.3 s (Turbo 4.9 s with its fixed cost). 256 blocks, 8,192 subproblems, 50 nodes per launch: objective 795 at 1.04 s wall (launch 7). The entailed-propagator list, as first written with one atomic per kept propagator, made nodes slower (4.4 ms) because restores reset it every time; with warp compaction the mean is 4.6 ms, so it does not help in this search and is to be reconsidered.
- Not done: proving 795 optimal on the GPU with many blocks (one block was still working on subproblem 8191 after 188,000 nodes in total), a free-time gate around the launches, launches under 1 ms.
- Turbo's own reference, party, default 256 blocks and 8,192 subproblems, 600 s limit (2026-11-24): 609,299 nodes, objective 795 found at 2.34 s, 7 subproblems searched and 8,184 skipped, `num_blocks_done=255` of 256: one block never finishes, so Turbo does not prove optimality in this configuration either; it ends on the time limit. - Time is the entity packet's HLC (2026-11-24): the GPU host stamps every reply (`hlc W`), takes the player's stamp on `run N W` and `status W`, and with `TURBO_EVENTS=FILE` appends `launch HLC START_NS DURATION_NS NODES`; the player stamps its commands and appends `slice HLC PLAN_MS RUN_MS`; `tools/turbo_profile.exs TRACE` checks the stamps only grow and splits GPU time, host gaps and planner time. The HLC has one millisecond of resolution and a launch is 0.1 to 0.6 ms, so the stamp orders events and the nanosecond fields time them. Scout through the player at 50 launches per slice: 630 launches, GPU time 70 ms of a 2,848 ms span (2.5 percent), launch mean 0.111 ms, p99 0.344 ms, max 0.501 ms, planner 85.8 percent of the slice time (13 slices, 227 ms each); stamps nondecreasing. Not yet stamped: the cluster's Erlang messages and the CPU guest host.
- Speed, incremental propagation (2026-11-24, M2): the cooperative kernel re-runs only the propagators of variables that changed. The host builds the variable-to-propagator lists (`var_start`, `var_props`); every successful `embed_a` puts its variable on the block's list of changed variables once (a flag per variable and an atomic append); a propagation round queues the propagators of the listed variables once each (a mark per propagator and a queue; a variable with more than 48 watchers is spread over all 256 threads, because one thread walking a variable watched by thousands of propagators made the first version 3 times slower than the full sweeps), runs them, and repeats until no variable is listed or the store fails; a failure clears the list. Everything that loads a store wholesale marks all variables changed: the start of a subproblem and a loaded checkpoint (state slot 29). The final fixpoint is unique, so the search is unchanged. Check: party 99,246 nodes: 49,616 failures, 5 solutions, 795, depth_max 200 (Turbo's numbers), 45.7 s against about 95 s before. Full party proof, one block, uncapped, through the planner player: 1,058,921 nodes, 529,456 failures, 5 solutions, 795, depth_max 206, exhaustive, launch wall 589.8 s (mean 0.359 ms, max 11.5 ms), whole unit 616.0 s, against Turbo's 953 s (1.55 times as fast) and our own earlier 915.6 s. Per node: about 14.5 rounds, 35,500 propagator runs against 8 full sweeps of 27,082 (about 217,000); on scout, whose sweeps are short, the rounds cost more than they save (mean launch 0.106 ms before, 0.120 ms now), so the gain is for the large levels. The kernel clock (`getRealtimeClockLow` at the leader) says 94 percent of a launch is propagation; the state record grew from 24 to 32 ints (slots 24 to 27 clock, 28 and 29 the changed list, 30 and 31 counters), so checkpoints from before this change do not load.
- Saga with incremental propagation (2026-11-24): one block, uncapped, through the player: 10,551 nodes, 5,241 failures, 35 solutions, 1537, exhaustive (equal to Turbo's 10,551 / 5,241 / 35), launch wall 30.2 s (mean 2.33 ms per node, max 10.1 ms) against Turbo's 113.3 s solve time: 3.7 times as fast.

- Speed, fewer barriers (2026-11-24): the lists of changed variables alternate between two buffers and the round counters between two slots, so a propagation round needs two barriers (three when a variable with many watchers is spread over the block) instead of seven. Same counts (party 3,000 nodes: 1,495 failures; 99,246 nodes: 49,616 failures, 5 solutions, depth_max 200), 99,246 nodes in 44.8 s against 45.7 s: 2 percent, so the barriers were not the cost. Per round (about 18 rounds per node, 1,900 propagators run per round, 7.5 microseconds to build the queue and 11 to run it, from the in-kernel clock): the rounds are bound by dependent global-memory loads on the one SM that a block occupies, not by synchronisation. The other SMs are used by more blocks: party with 256 blocks and 8,192 subproblems (50 nodes per launch) reaches 795 at 102 ms (launch 7) against 1.04 s before the incremental propagation and Turbo's 2.34 s of wall time.
- Speed, work moves between blocks (2026-11-24, M2, constant work): with 256 blocks and 8,192 subproblems the proof used to wait on one block (255 of 256 done, then 50 nodes per launch for minutes), because after the bound 795 is found the whole remaining tree sits in the last subproblem, and a deeper split (power 18) leaves it there too. Now every launch runs the same exchange on the host between launches (no block is running, so plain copies are safe): each block that has finished takes the shallowest decision of a busy block whose second child is unexplored; the busy block gets that child emptied (its next try fails at once), the idle block starts from the busy block's snapshot with the decisions on the path applied (the same restart path as a checkpoint load: state slot 29, all variables changed). With no idle block, or no open decision, nothing moves, and nothing is a flag. Party, 256 blocks, power 13, 50 nodes per launch: done in 139 launches, 3.77 s of launch wall time, 9,225 handoffs, 1,088,306 nodes in total (the single block needs 1,058,921), best objective 795 (the proven optimum), every printed block exhaustive; Turbo needs 953 s with one block and does not finish with 256, and our single block took 616 s. Saga with the same settings: done, best objective 1537 (the optimum), 94 launches, 26.4 s, 2,296 handoffs, 1,106,064 nodes against 10,551 for one block: its optimum is only found near the end of the search, so the blocks search without a bound and do 100 times the nodes; there 256 blocks are no faster than one (30.2 s). The node counts of a parallel run are not equal to the sequential ones (the bound reaches blocks at different times); the gate for it is the proven optimum.
- HLC across the cluster (2026-11-24): every message of `tools/turbo_cluster.exs` (hello, problem, frames to and from the host) carries the sender's hybrid logical clock as a last element (`service/turbo-cluster.asyncapi.yaml` has the field), each process keeps its own clock and merges what it receives, a finished subproblem is attributed by the smaller stamp (a copy that arrives later but carries the smaller stamp takes the win and a `reorder` event is logged), and `TURBO_EVENTS=FILE` appends `cluster HLC NODE EVENT DETAIL` lines (hello, assign, send, finish, steal, reorder) that `tools/turbo_profile.exs` merges by stamp. The variable is named `TURBO_EVENTS` because `TURBO_TRACE` belongs to the libriscv host's instruction trace (which stops the guest). - Constant work, the resync flag is gone (2026-11-24): the kernel no longer has a "propagate everything once" flag in the state. A loaded checkpoint and a block that takes over work get their list of changed variables written as data by the host (every variable, flag set, count n), and the kernel runs the same loop it always runs. Checks: scout through the player, two slices, checkpoint, resume: 629 nodes, 511; party 99,246 nodes on one block 49,616 failures, 5 solutions, depth_max 200 in 45.5 s; party on 256 blocks done in 139 launches, 4.1 s, 9,284 handoffs, best objective 795. The two-path walk of a variable's watchers (few: one thread; many: the whole block) stays: a flat list of (variable, watcher) pairs needs a prefix sum and a binary search per pair, which costs more dependent loads than the branch it removes.
- Stealing as a queue machine, no clock (2026-11-24): the first cluster test depended on timing (a throttled node, a steal threshold of 500 ms, a speed ratio of 1.5 over a measured rate) and failed once in CI with no steal; a longer delay would only move the race. The coordinator is now a queue machine: pending subproblems (retries first, then the counter), in-flight jobs with a sequence number given at assignment, and per node the count of finished jobs. A node that asks gets the head of the queue; with the queue empty and jobs in flight it takes the oldest in-flight job, not yet stolen, of a node that has finished fewer jobs than it has; with nothing in flight it is told `D`. The worker is an OTP `gen_statem` (`Turbo.Worker` in `tools/turbo_cluster.exs`, callback mode state functions) with the states ready and held: with `--hold-first-job` its first assignment is kept (a node that is busy elsewhere), and a cancel while holding is answered for the host with the finished frame; `--die-at-first-job` replaces the environment variable. `--steal-after-ms`, the measured rate and the speed prior are gone; `--no-steal` is the only switch. The test (scout, 32 subproblems, one plain node, one that holds its first job, one that dies on its first job) has no delay in it: six runs in a row, locally, each with one steal, a lost node redone, objective 511, about 6.5 s. The CI workflow uses only scout, the smallest level.

## Many blocks give the same answer (2026-11-24, mission item 1)
`tools/turbo_blocks_check.exs` solves generated Party Saga worlds (track scout, sizes 1 and 2, seeds 1 to 25, compiled with MiniZinc's own library and dumped by `frontier_frontend`) on one GPU block, on 8 blocks (8 subproblems) and on 256 blocks (256 subproblems), and requires that every run ends, that every block reports an exhaustive search (`exhaustive blocks N of N`, new in the host's report) and that the best objective is the one block's. Result: 50 of 50 worlds. Size 1 worlds are too small to move work (29 to 51 nodes, 0 handoffs); all 25 size 2 worlds moved work on 8 blocks (1,023 handoffs in all) and on 256 blocks (3,050), the largest with 19,791 nodes on one block, 21,466 on 8 and 22,954 on 256. Before this the handoff path rested on three matching optima (scout, party, saga). `tools/turbo_solve.exs --input-only` writes the solver input without building the CPU solver, so a world costs seconds. Local only: it needs the GPU.

## One handoff rule and one default for many blocks (2026-11-24, mission item 2)
Saga on 256 blocks did about 100 times the nodes of one block and was no faster, so the handoff rule, the up-front split, the nodes per launch and the block count were measured (GPU launch time = launches times the mean launch, duty 50; one block: party 616 s, saga 30 s):

| setting | party | saga |
|---|---|---|
| 256 blocks, 8,192 subproblems, shallowest open decision (the merged rule) | 1.4 s, 1,088,155 nodes | 26.5 s, 1,094,713 nodes |
| same, deepest open decision | 1.5 s | 23.3 s, 1,052,937 |
| 256 blocks, no split, shallowest | 1.5 s, 1,068,063 | 22.4 s, 1,010,203 |
| 256 blocks, no split, deepest | 1.5 s, 1,073,841 | 16.4 s, 945,995 |
| same, 5 or 15 nodes per launch | 2.4 s and 1.8 s | 43.6 s and 40.0 s |
| no split, deepest, 16 blocks | 12.3 s, 1,061,171 | 11.6 s, 84,749 |
| 32 blocks | 6.1 s, 1,064,342 | 11.2 s, 153,702 |
| **64 blocks (the default)** | **3.5 s, 1,064,629** | **13.2 s, 292,370** |
| 128 blocks | 1.9 s, 1,067,657 | 13.8 s, 535,024 |

Findings. The handoff rule and the split are small effects (the deepest open decision is a little better on saga and level on party; with no split the blocks are fed by handoffs only, so the start needs no parameter). The large effect is the block count on saga: it is a chain of 35 improving solutions on one deep path, so extra blocks do speculative work with no bound (16 blocks do 8 times the nodes of one block and are 2.6 times as fast; 256 blocks do 90 times and are 1.8 times as fast), while party has parallel width and keeps gaining up to 256. No count is best for both, so the default is 64: party in 3.5 s (about 175 times as fast as one block and 270 times Turbo's 953 s), saga in 13.2 s (2.3 times as fast as one block, 8.5 times Turbo's 113 s). Fewer nodes per launch only add handoffs. The code has one rule (the deepest open decision of the block that has the deepest one; the experiment switch is gone), the default is 64 blocks and `--power 0` in `tools/turbo_gpu.exs` and `tools/turbo_player.exs`, and `--blocks` and `--power` stay as data. `tools/turbo_blocks_check.exs` with the new rule and default: 50 of 50 generated worlds give the one-block optimum on 8 and on 64 blocks, every block exhaustive, 1,412 handoffs on 8 blocks and 2,746 on 64 in the 25 size 2 worlds.

## Stop and resume on many blocks (2026-11-24, mission item 2a)
The GPU host's `save` and `load`, with handoffs in flight: run some launches on 8 or 64 blocks, `save`, quit, start a new host process, `load`, run to the end. scout, 8 blocks, saved after 3 launches (410 nodes): resumed, 15 further handoffs, done with 1,974 nodes, every block exhaustive, objective 511. party, 64 blocks, saved after 40 launches (80,378 nodes, bound 795): resumed, 5,467 further handoffs, done with 1,065,753 nodes, 64 of 64 exhaustive, 795. saga, 64 blocks, saved after 30 launches (80,800 nodes, bound 1627): resumed, 610 further handoffs, done with 279,070 nodes, 64 of 64 exhaustive, 1537. (The loaded state carries no list of changed variables, so the host writes every variable as changed for every block, as data.) What does not exist: an on-disk checkpoint of the CPU guest. `turbo_host` keeps the guest alive between 64 Hz windows inside one process (the windows and their budgets are verified under binary translation: 1,035 windows against 1,955 interpreted, same search), but it never wrote a checkpoint of the guest's memory to disk; the earlier plan item "serialize_to" was not built. The GPU engine, which is the one that matters for the proofs, has it.
